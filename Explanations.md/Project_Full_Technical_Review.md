# Dungeon Escape: Comprehensive Project Architecture Narrative

This document provides a formal, long-form technical review of the "Dungeon Escape" project. It explores the architectural decisions, logical frameworks, and individual class responsibilities in a narrative format, suitable for a formal academic report or project assessment.

---

## I. System Orchestration and the User Interface Layer

The foundational structure of the application is built upon a hybrid architecture that bridges two of Java's primary graphical frameworks: Swing and JavaFX. The **Main.java** class serves as the primary orchestrator for this relationship. It is responsible for initializing the game’s physical window using a `JFrame` and managing the transitions between different application states. When a game session concludes, the `Main` class facilitates a thread-safe return to the user interface by utilizing the `Platform.runLater()` utility. This is a critical technical requirement because JavaFX operates on a separate application thread from the standard Swing thread; without this careful orchestration, the application would encounter significant concurrency conflicts or crashes.

Complementing this orchestration is the **GameMenu.java** class, which acts as the project’s frontend. Unlike the core game which uses the pixel-focused Swing library, the menu is built using JavaFX to provide a modern, high-fidelity experience with CSS-like styling and smooth transitions. To ensure that the menu looks consistent across all screen sizes, we implemented a scaling root within a `StackPane`. This allows the UI elements to resize proportionally while remaining perfectly centered. Furthermore, the `GameMenu` is the point where the player’s mode selection occurs, and it is responsible for "tunneling" these choices into the game engine through arguments passed during class initialization.

## II. The Core Engine and Interactive Loop

At the heart of the gameplay experience is the **GamePanel.java** class, which functions as the master controller for the entire game world. It implements the `Runnable` interface to facilitate a high-performance game loop that targets a consistent sixty frames per second. The technical complexity of this class lies in its management of the rendering pipeline and the "Adaptive Scaling Engine." To ensure that the game remains playable on modern high-resolution monitors without stretching the graphics, the `GamePanel` utilizes a logical coordinate system of 960x720 pixels. By applying an affine transformation via `Graphics2D.scale()` during the drawing phase, the engine automatically maps these logical coordinates to the actual pixel dimensions of the window. This allows the game to support window maximization and custom resizing while maintaining a perfect aspect ratio for all game assets.

Input management is handled asynchronously by the **KeyHandler.java** class. By implementing the `KeyListener` interface, this class captures hardware interrupts from the keyboard and translates them into a set of Boolean flags. This architectural decision is significant because it decouples the physical act of pressing a key from the logical calculation of movement. By separating these concerns, the game can handle multiple simultaneous inputs—such as moving diagonally while simultaneously attempting to pause the game—without the input lag or ghosting issues that often plague simpler implementations.

## III. World Generation and Navigation Logic

The dungeon environment is procedurally generated by the **Map.java** class. Each level is unique, featuring a randomized distribution of wall tiles that provide a different challenge every time a player enters a new floor. A key technical feature of this class is the "Path Safety Guarantee." During generation, the map employs a carving algorithm that ensures a traversable route exists between the player's starting position and the exit. Without this check, the procedural randomization could potentially trap the player in an unreachable area, a common pitfall in procedural game design. Additionally, the map is responsible for the dynamic placement of items and exits, ensuring they are placed at a mathematically significant distance from the player to maintain a fair but challenging difficulty curve.

Intelligent entity movement is made possible by the A* (A-Star) pathfinding algorithm, which is supported by the **Node.java** data structure. Each `Node` represents a single walkable tile in the dungeon grid and stores the costs associated with moving through that tile. The "gCost" represents the distance from the start, the "hCost" represents the estimated distance to the player using Manhattan Distance, and the "fCost" represents the combined efficiency of that specific path. By maintaining a network of these nodes and using them to backtrack through "Parent" references, the enemy AI can navigate complex mazes to find the most efficient route to the player. This system is technically superior to simple line-of-sight algorithms because it allows enemies to "see" around corners and plan their movements in advance.

The visual properties of the dungeon are abstracted by the **Tile.java** class. This lightweight data class allows the game to treat different grid elements as a unified array of objects. By storing collision and color data within each tile, the rendering engine and the physics engine can query the map independently to determine whether a specific coordinate is walkable or needs to be drawn. This decoupling makes it easy to add new environmental elements, such as locked doors or decorative tiles, without needing to rewrite the core map logic.

## IV. Game Entities and Entity Physics

The player’s presence in the world is managed by the **Player.java** class. One of the most significant technical refinements in this class is the "Independent Axis Collision" logic. In many basic games, collision checks are performed globally, which causes a player to stop moving entirely if they hit a wall diagonally. In our implementation, however, the collision check is split into separate X and Y updates. This allows the player to "slide" along a horizontal wall even if they are holding a vertical movement key, creating a much smoother and more professional feel. Additionally, the player’s class manages sprite-based animations, dynamically selecting directional images and centering them over a physical hitbox that is slightly smaller than the visual asset to prevent "snagging" on corner tiles.

Opposing the player is the **Enemy.java** class, which operates as a state-driven machine. The enemy AI switches between a "Wander" state, where it roams the map to find interest points, and a "Chase" state, which is triggered when the player enters a specific detection radius. To manage performance, we implemented a "Pathfinding Throttling" system that ensures enemies only recalculate their A* path every fifteen frames. To prevent multiple enemies from overlapping into a single "death ball," we also implemented a displacement force system. This logic checks the proximity of other enemy entities and applies a small repulsion force, ensuring that they maintain a natural group structure that remains challenging for the player to navigate.

## V. Data Persistence and Record Keeping

Finally, the game ensures its longevity through a persistent data layer managed by the **ScoreManager.java** class. This class is responsible for the permanent storage of high scores using a Comma-Separated Values (CSV) format. A critical technical detail of this system is its "Backward Compatibility" engineering. As the project evolved and we added more fields to the scoreboard—such as Game Mode and Coin counts—the `ScoreManager` was designed to safely parse older data files without crashing. It uses length-checks on the CSV parts to determine which version of the score file it is reading and applies default values for any missing fields.

Each individual record in the system is represented by the **ScoreEntry.java** class. This simple data model encapsulates all the metadata for a single game run, including the player's name, their final score, the level they reached, the mode they played, and their specific objectives achieved. By using this object-oriented approach to data, the game can easily sort and display the top ten scores in the JavaFX menu, providing a clear competitive goal for the player.
